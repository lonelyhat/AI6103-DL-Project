## 3. ID 规则

### 3.1 为什么不直接用官方 ID

官方 ID 带有答案信息，属于**标签泄漏**：

- 证据会话 ID 带 `answer_` 前缀（如 `answer_eaa8e3ef_1`）；官方检索 ID 里，证据会话内无证据的轮被改成 `noans_`
- 填充会话 ID 带数据来源（`sharegpt_`、`ultrachat_`），一看就知道与用户个人信息无关

选择器只要能看到这些字符串，就可能“偷看”证据，结果会虚高且不能说明方法有效。因此官方 ID 只保留在 `map/` 中。

### 3.2 规则

本组 ID **只用位置编号**，不含任何内容信息。位置均从 0 开始，补零 3 位，分隔符用 `-`（题号只含 `0-9a-z_`，不会冲突；`-` 在文件名、shell、JSON 中都安全）。

| 层级 | 格式 | 例子 | 定义 |
| --- | --- | --- | --- |
| 会话 | `{qid}-s{i:03d}` | `2318644b-s004` | `haystack_sessions` 第 i 个 |
| 消息 | `{qid}-s{i:03d}-m{p:03d}` | `2318644b-s004-m003` | 会话内原始位置 p，**不论角色** |
| 轮 | `{qid}-s{i:03d}-t{k:03d}` | `2318644b-s004-t001` | 会话内第 k 条用户消息 + 紧随的下一条消息 |

要点：

- **轮是选择单元**，定义与官方回答脚本一致（`run_generation.py:119-131`：用户发言 + 下一条，不检查下一条角色）。
- **消息 ID 按原始位置**而非“u/a + 轮号”：数据中 1942 个会话以助手开头、14 个会话有连续同角色消息，按角色编号会撞名。
- **ID 顺序 ≠ 时间顺序。** `haystack_sessions` 并不总是按时间排列：开发题 13/40 道、全量 211/500 道存在日期倒序，首批的 `1cea1afa`、`gpt4_7a0daae1` 也在其中。ID 只负责唯一定位，**按时间排列材料时用 `sort_key`**（见下）。
- **`sort_key` = `[ISO 日期时间, 会话位置, 用户消息位置]`**，排序顺序为：先按实际日期时间，同一时刻再按原会话位置，再按轮的位置。95/500 道题存在完全相同的会话时间戳，因此需要后两级排序键，时间也不能单独充当 ID。
- **重叠轮。** 连续两条用户消息时，后一条同时属于两个轮（前一轮的“下一条”，以及它自己开头的轮）。消息映射因此保存**全部**所属轮 `turn_ids`。开发题中有 9 条这样的消息，都在 `4c36ccef` 里，目前都不是证据；全量中有 24 条，也都不是证据。
- 一道题最多 62 个会话、单会话最多 132 条消息，3 位补零足够。

### 3.3 与官方 ID 的映射

`map/{qid}.turns.jsonl` 每轮一行：

```json
{"turn_id": "2318644b-s000-t001", "session_index": 0, "session_date": "2023/05/20 (Sat) 16:16",
 "session_datetime": "2023-05-20T16:16", "sort_key": ["2023-05-20T16:16", 0, 2],
 "message_ids": ["2318644b-s000-m002", "2318644b-s000-m003"],
 "official_session_id": "sharegpt_7Ezwt1J_31", "official_corpus_id": "sharegpt_7Ezwt1J_31_3"}
```

`official_corpus_id` 按官方规则生成：`<会话id>_<用户消息位置+1>`，证据会话中用户消息无 `has_answer` 时 `answer` 改为 `noans`（`run_retrieval.py:217, 224`）。**B 线拿官方检索日志后，用 `official_corpus_id → turn_id` 转换，输出给 D 线的文件只保留 `turn_id`。**

`map/{qid}.messages.jsonl` 每条消息一行：`message_id, turn_ids（列表，可能为 0、1、2 个）, session_index, position, role, official_session_id`。`turn_ids` 为空即不可达消息。

`eval/dev_eval.jsonl`：

```json
{"question_id": "2318644b", "question_type": "multi-session", "is_abstention": false, "answer": "$270",
 "answer_session_ids": [...], "evidence_session_indices": [16, 20],
 "evidence_message_ids": ["2318644b-s016-m000", "2318644b-s020-m002"],
```

`unreachable_evidence_message_ids`：不属于任何轮的证据消息（会话开头的助手消息等），任何选择办法都选不到。全部 500 题中有 3 条（`58470ed2`、`352ab8bd`、`7a8d0b71`），**40 道开发题中没有**。A02 计算保留率时这类证据仍计入分母，并归入“候选没有找齐”。

## 5. 发现的问题（需要相关同学知道）

1. **会话 ID 本身就泄漏信息**，不只是轮 ID（第 3.1 节）。B01 文档第 7 节第 2 条可据此补充。
2. **官方轮级证据标记会漏掉助手证据。** 官方只看用户消息有无 `has_answer`，因此证据在助手回复里的轮会被标成 `noans`。例：`4c36ccef` 的证据轮 `s046-t001`，官方 ID 为 `noans_ultrachat_448704_3`。如果用官方内置的轮级 recall，single-session-assistant 题的证据会被算漏。**A02 应以消息级 `has_answer` 为准**（本组 `evidence_turn_ids` 已按此生成）。
3. **旧存档 ID 未对齐。** baseline_v1 存档和 E01 输入使用 `m00000` 形式的单元编号，其定义尚未确认，与本规则的对应关系**待确认**；新任务统一使用本规则。
4. **D02 拼接材料须按 `sort_key` 排序**，不能按 ID 排，也不能只按日期字符串排（同一时刻会乱序，与 B01 第 3.2 节第 6 点一致）。
5. **D02 拼接时需对消息去重**：同时选中两个重叠轮时，共享的那条用户消息会出现两次。是否去重、怎样计入预算，请 D 线确定后写进 D02。
